# Каталог ODP-профилей

🇷🇺 Русский · 🇬🇧 [English](../README.md)

> **Нормативный источник — английский `README.md` и `SPECIFICATION.md`.** Перевод сделан для
> удобства и может содержать ошибки; считайте его информационным.

**CSV-формат для списка ODP-профилей, чьи владельцы опубликовали свой ID на собственном сайте —
и пример такого файла, который можно скопировать.**

Если вы делаете приложение на [ODP](https://github.com/object-digital-passport/specifications),
протокол даёт вам ID профиля вида `B-029-384-751-224` и больше ничего. Имён в блокчейне нет
намеренно: иначе кто угодно зарегистрировался бы как «Adidas». Поэтому приложение, которое хочет
показать, *кто* выпустил паспорт, каждый раз решает одну и ту же задачу — найти, где эта
организация опубликовала свой ID, и проверить, что он там всё ещё есть.

Этот репозиторий — та же работа, сделанная один раз, в файле, который можно прочитать глазами.

---

## Прочитайте это, прежде чем чему-то здесь доверять

- **Строки отбирает мейнтейнер репозитория.** Это кураторская подборка, а не истина протокола.
- **Отсутствие не значит ничего.** Большинства честных организаций здесь нет. Никогда не
  трактуйте «нет в каталоге» как предупреждение о ком-либо.
- **Наличие ничего не гарантирует.** Оно значит, что ID был найден опубликованным на этом
  домене. Не значит, что организация честна, платёжеспособна или что её паспорта точны.
- **Протокол не знает о существовании этого файла.** Ни минт, ни proof, ни результат проверки
  от него не зависят. См. `SPEC.md` §4 в репозитории спецификации.

## Данные в примере — вымышленные

Все строки в `odp-directory-v0.6.csv` используют зарезервированные для документации домены
(`example.com`, `example.org`, `example.net`, RFC 2606) и выдуманные ID профилей. **Ни одна
реальная организация здесь не указана, и ни с кем не связывались.** Строки существуют, чтобы
показать, как выглядит каждая колонка и каждый статус, включая состояния отказа. Запуск
`npm run recheck` по ним отрапортует, что всё недоступно, — и это правильно: эти домены не
отдают ничего.

## Это пример. Сделайте свой.

В этом репозитории нет ничего привилегированного. Это список одного мейнтейнера в формате,
который может переиспользовать кто угодно, — и предполагаемый способ им пользоваться состоит
**не** в том, чтобы зависеть от этого файла, а в том, чтобы вести свой.

Форкните, удалите все строки — и у вас рабочий каталог для вашего проекта:

1. Направьте `tools/config.json` на тот реестр, против которого вы проверяете (`chainId`,
   `registryAddress`, `csvFile` с именем под эту генерацию).
2. Добавляйте свои строки по своим правилам приёма. Строже, чем здесь, мягче или вообще
   закрытый список партнёров, с которыми у вас уже есть договоры, — решаете вы.
3. Пусть workflow ежедневно перечитывает точки и публикует `directory.json`.
4. Читайте этот JSON из своего приложения.

Ваш каталог отвечает только перед вами, и пользователи доверяют ему ровно настолько, насколько
доверяют вам. В этом и смысл: у ODP нет центрального реестра, поэтому любой каталог — чьё-то
редакторское мнение о том, кого стоит показывать. Здоровее, когда таких каталогов много и у их
владельцев разная репутация, чем когда один тихо становится авторитетом.

Единственное, что не в вашей власти переопределить, — что каталогу разрешено **утверждать**.
Правила статусов в [SPECIFICATION.md](SPECIFICATION.md) существуют ради того, чтобы пользователь,
переходящий между двумя приложениями с двумя разными каталогами, не видел `unreachable` как
обвинение в одном и как молчание в другом. Их сохраните, всё остальное меняйте.

## Файлы

| Файл | Что это |
|:--|:--|
| `odp-directory-v0.6.csv` | Сам каталог. Одна строка на профиль. Правится руками. |
| `directory.json` | Те же данные в JSON, собирает CI. **Из приложения читайте его.** |
| `tools/config.json` | Какой реестр описывает файл: сеть, адрес, линия спеки, пороги. |
| `docs/SPECIFICATION.md` | Формат, нормативно. Выдержка из спецификации ODP. |
| `tools/` | Бот перепроверки и его служебное состояние. |

Имя файла несёт генерацию реестра (`v0.6`). ID профиля ничего не значит без реестра, который его
выдал: тот же кошелёк получает **другой** ID в другом развёртывании. Когда выйдет v1, рядом
появится второй CSV; ничего не переписывается.

## Колонки

| # | Колонка | Смысл |
|:--|:--|:--|
| 1 | `profileId` | `T-NNN-NNN-NNN-NNN`. Ключ. По нему сортировка. |
| 2 | `profileType` | `C` / `B` / `P` / `M`. Повторяет префикс, чтобы файл фильтровался. |
| 3 | `displayName` | **Не авторитетно.** Ярлык для удобства. Не принимайте по нему решений. |
| 4 | `evidenceKind` | `website` или `social`. |
| 5 | `evidenceUrl` | Страница, которую человек откроет и увидит ID. |
| 6 | `evidenceHost` | Хост из `evidenceUrl`. Для строк `website` — туда смотрит бот. |
| 7 | `checkMethod` | `auto` (бот перечитывает ежедневно) или `manual` (только человек). |
| 8 | `status` | См. ниже. |
| 9 | `lastCheckedAt` | Когда бот смотрел последний раз. Пусто для ручных строк. |
| 10 | `lastVerifiedAt` | Когда последний раз смотрел человек. |
| 11 | `archiveUrl` | Снимок, подтверждающий, что человек видел. Обязателен для ручных строк. |
| 12 | `addedAt` | Когда строка попала в файл. |

Намеренно **отсутствуют**: связи родитель-ребёнок (читайте `getAffiliatedParent` из контракта —
файл разошёлся бы с ним), сеть и адрес реестра (они в `tools/config.json` и в имени файла), кошелёк
(читается через `getCreator` из контракта).

## Что приложение обязано делать со `status`

| `status` | Показывать |
|:--|:--|
| `active` | Идентичность организации можно показать. |
| `unreachable` | **Ничего.** Ни имени, ни предупреждения. |
| `unverifiable` | Имя вместе с датой последней ручной проверки. |
| `removed` | Заметное предупреждение на записи. |
| `withdrawn` | Ничего. Строка хранится только как история. |

`unreachable` и `removed` — не одно и то же, и смешивать их нельзя. Сайт, который не открылся,
не говорит ни о чём: серверы падают. ID, **намеренно удалённый** со страницы, которая по-прежнему
открывается, — это поступок. Считать первое вторым значит публично обвинять честные организации
в подделке из-за выходных с недоступным сайтом.

Предупреждение **никогда** не выставляется строке, которую бот не смог прочитать изначально.
Отсутствие находки — не находка.

## Как работает автоматическая проверка

Бот не парсит человеческую страницу. Он читает фиксированную точку на собственном домене
организации:

```
https://<domain>/.well-known/odp.json
```

```json
{
  "odp": 1,
  "chainId": 137,
  "registry": "0x012aC6393464A73EC16131D701ff2e000695b91b",
  "profiles": [{ "profileId": "B-029-384-751-224", "wallet": "0x742d35Cc…4438f44e" }]
}
```

Парсинг видимой страницы ломается двумя важными способами: страница, отрисованная на JavaScript,
прячет ID от любого не-браузера, а страница, куда может писать кто угодно (форум, раздел
сообщества), помещает текст злоумышленника на официальный домен. Статичный файл по
зарезервированному пути (RFC 8615) читается без браузера, а записать его может только тот, кто
управляет сервером.

Организации (`B`, `M`, `P`) **обязаны** его отдавать; физические лица (`C`) — по возможности,
если у них есть домен. Где точки нет — соцсеть, страница на клиентском рендере — строка живёт в
ручном режиме со снимком и протухает через 183 дня.

## Как попасть в список

1. Опубликуйте ID профиля и кошелёк на своём сайте, как требует `SPEC.md` §3.
2. Добавьте `/.well-known/odp.json` на этот домен.
3. Откройте pull request с одной строкой. См. [CONTRIBUTING.ru.md](CONTRIBUTING.ru.md).

PR может открыть кто угодно на любой профиль — доказательство всё равно публичное. Мейнтейнер
мержит после того, как убедится, что домен настоящий, и CI зелёный.

## Локально

```bash
node tools/validate.mjs     # все правила формата
node tools/build.mjs        # пересобрать directory.json
node tools/recheck.mjs --dry-run
```

Node 22+, без зависимостей.
